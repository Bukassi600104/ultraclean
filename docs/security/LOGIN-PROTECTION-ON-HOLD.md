# Login protection preparation, activation on hold

The user chose to keep security activation on hold while other improvements ship. Nothing here changes existing login, passwords, sessions, accounts, permissions or recovery settings. No application caller imports the prepared modules. `LOGIN_PROTECTION_ACTIVE` is a literal false; it is not an environment switch to activate an incomplete implementation.

## Prepared and testable

`lib/login-protection-policy.ts` defines the approved rolling windows: five failed passwords in 15 minutes, escalating 15/30/60-minute locks within 24 hours; 20 IP attempts per minute; the 50th IP failure in 15 minutes starts a 15-minute restriction; recovery three/account/hour and ten/IP/hour. Blocked attempts preserve expiry. Success clears failures but retains escalation history. `allowed` means proceed to password verification, never successful authentication.

The pure module also checks staff-unlock eligibility and translates protection storage failures into a generic unavailable error. `lib/login-protection-identity.ts` supplies keyed HMAC subjects for existing and nonexistent accounts alike. The password must never be normalized, logged or passed to counter storage. IP canonicalization and trusted-source validation remain gateway responsibilities.

Run `node scripts/test-login-protection-policy.mjs` and `node scripts/test-login-protection-sql.mjs`. Policy tests make no network/database/auth calls. SQL tests use synthetic in-memory PGlite via the existing test helper, never a production connection. Both pass. SQL checks cover syntax, hook grants and table isolation, fifth-failure 15/30/60-minute escalation, expiry, stable blocked timestamps, successful resets, 20 accepted IP reservations out of 24 queued requests, the 50th IP failure, paired recovery limits and expiry, and unchanged fixture profiles. PGlite serializes requests; this is not multi-connection contention proof. Neither suite proves actual provider integration, email delivery or direct bypass protection.

## Database proposal, deliberately not deployable

`login-protection-preparation.sql` sits outside the migration directory and ends in ROLLBACK. It proposes private row-locked counters, an append-only-intended audit store, a password hook returning boolean `should_logout_user:false`, a window primitive and atomic paired recovery reservations. It changes no existing tables or records. The isolated test replaces its final rollback with commit in synthetic PGlite only. SQL syntax and the listed policy/grant checks pass; managed Auth hook transaction persistence and real concurrent connections remain unverified. Do not move it into migrations as-is.

The paired recovery routine reserves both quotas in deterministic key order and consumes neither when either denies; login, failure and recovery counters have distinct namespaces. Before activation, implement privileged gateway wrappers; deduplicate password-attempt completion using private request receipts; authenticate all caller identities server-side; and restrict audit writes to the unlock routine. Unknown account password attempts still need generic keyed counters and responses without leaking existence. The actual-user hook and gateway must never count one password failure twice.

An unlock endpoint must check an active admin and an allowed staff role, perform fresh password verification through the same protection path, and bind that verification to the actor/target/action in a short-lived single-use server record. Do not trust a client timestamp or role. The pure eligibility function is only a policy check. In one transaction, consume reauthentication proof, lock and clear target restriction/failures, retain escalation history, and append actor/target/reason/time audit. Never change suspension, role, password or session rows. Staff cannot unlock admins. Reject on any storage/audit error. Separate verification and privileged clients to avoid replacing the CEO session.

## Remaining gates and work

1. Supabase [Team pricing](https://supabase.com/pricing) currently starts at $599/month, with potential usage charges; obtain account-specific approval before purchase. The [password verification hook](https://supabase.com/docs/guides/auth/auth-hooks/password-verification-hook) requires Team/Enterprise. No subscription was changed.
2. The hook has user ID and password validity but no IP. It can protect direct account-password attempts. It cannot enforce the exact custom IP failure or recovery quotas on direct Supabase calls. Resolve provider-supported direct-path coverage before claiming complete protection. Native [/token rate limits](https://supabase.com/docs/guides/auth/rate-limits) also affect refresh/PKCE; do not tighten them blindly.
3. Use [Vercel trusted request headers](https://vercel.com/docs/headers/request-headers) with validated normalized IPs, not arbitrary supplied headers in another environment. Supabase end-user forwarding requires enabled forwarding and a server secret key; never expose that key.
4. Verify CEO recovery mailbox ownership, SMTP/send-email capability, exact redirect allowlist, delivery and reset completion. Existing `change-email` auto-confirms with `email_confirm:true`; a database confirmation timestamp alone is insufficient proof of ownership. No recovery endpoint or provider integration is included here.
5. Wire and test all four login forms plus password/email reauthentication only after readiness. Existing support roles also require coverage. Keep current sessions during failed attempts elsewhere. Generic errors and timing must not enumerate accounts. Provider faults are not bad passwords. Enabled protection must fail closed on storage errors.
6. Rehearse the future additive migration and parallel attempts on isolated data; test fifth/50th thresholds, expiry, 24-hour escalation, successful login, shared IP, spoofed headers, direct bypass, active-session refresh, unknown accounts, paired recovery limits, idempotent completions, staff unlock and suspended accounts. Then review production preservation evidence before a separately approved activation.

This is policy preparation, not installed or complete login protection.
